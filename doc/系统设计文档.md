# 系统设计文档：男妃AI超级智能体应用平台

---

## 一、需求分析

### 1.1 功能性需求

#### AI 恋爱大师（情感咨询场景）

| 编号 | 功能 | 描述 |
|------|------|------|
| F1 | 多轮对话 | 基于 chatId 维持会话上下文，支持同一用户多轮交流 |
| F2 | 角色扮演 | System Prompt 设定为恋爱心理专家，覆盖单身/恋爱/已婚三种状态 |
| F3 | RAG 知识库增强 | 检索本地 Markdown 文档 + 阿里云知识库，为回答注入专业知识 |
| F4 | 查询重写 | 用户输入经 LLM 改写为更适合检索的形式 |
| F5 | 文档关键词增强 | 文档入库时由 AI 自动提取关键词元信息 |
| F6 | 流式响应 | SSE 实时推送文本块，模拟打字机效果 |
| F7 | 对话记忆持久化 | 聊天记录存储到文件，支持滑动窗口（最近 N 条） |
| F8 | 结构化报告 | 可生成恋爱建议的 JSON 结构体（`LoveReport` record） |

#### AI 超级智能体（通用任务执行场景）

| 编号 | 功能 | 描述 |
|------|------|------|
| F9 | ReAct 循环执行 | 思考（Think）→ 行动（Act）的多步自主推理，最多 20 步 |
| F10 | 网络搜索 | 调用百度搜索引擎获取实时信息 |
| F11 | 网页抓取 | 使用 jsoup 抓取指定 URL 的网页内容 |
| F12 | 文件读写 | 读取和创建本地文件 |
| F13 | PDF 生成 | 将内容输出为 PDF 文档（支持中文） |
| F14 | 资源下载 | 下载互联网资源到本地 |
| F15 | 终端执行 | 在系统终端执行命令 |
| F16 | 主动终止 | Agent 可自主判断任务完成并调用 terminate 工具结束 |
| F17 | 结构化事件推送 | 8 种事件类型（思考/工具调用/工具结果/回答/错误等）实时推送到前端 |
| F18 | 执行轨迹可视化 | 前端实时展示每一步的思考、工具调用参数、结果 |
| F19 | MCP 扩展工具 | 通过 MCP 协议接入外部图片搜索服务 |

### 1.2 非功能性需求

| 类别 | 需求 | 当前实现 |
|------|------|---------|
| **响应延迟** | SSE 流式输出，用户感知延迟 < 2s | ChatClient stream + SseEmitter |
| **会话保持** | 支持多会话并行 | 基于 chatId 隔离的 Kryo 文件存储 |
| **可扩展性** | 工具/模型/知识库可灵活增删 | @Tool 注解 + ToolRegistration + 多策略 RAG |
| **前端体验** | 实时展示 AI 执行过程 | AgentTraceCard 结构化事件渲染 |
| **部署简单** | 单体部署，低运维成本 | 单 Spring Boot 进程 + 单 Vue SPA |
| **成本控制** | 开发/演示阶段低 Token 消耗 | 可选开关 ReReadingAdvisor 等 Token 增强 |

### 1.3 约束条件

| 约束 | 说明 |
|------|------|
| 团队规模 | 个人开发者 |
| 当前阶段 | 学习/演示项目，非生产环境 |
| 模型限制 | 通义千问 qwen-plus，有 RPM/TPM 限制 |
| 网络环境 | 国内网络，需避免被墙的 API |
| 存储约束 | 无数据库依赖（文件存储为主） |

## 四、技术选型的取舍点分析

### 4.1 LLM 框架选择：Spring AI Alibaba vs LangChain4j vs 自研

| 维度 | Spring AI Alibaba ✅ | LangChain4j | 纯自研 |
|------|---------------------|-------------|--------|
| Spring 生态融合 | 原生支持 DI/AOP/自动配置 | 需手动集成 | 完全自主 |
| 国内模型支持 | DashScope 原生适配 | 需自定义 Provider | 需自行封装 |
| RAG 抽象 | 内置 Advisor 链 + VectorStore | 内置 Chain 模式 | 需自行设计 |
| MCP 协议 | 内置 MCP Client/Server 模块 | 社区支持 | 需自行实现 |
| 学习曲线 | 低（Spring 开发者友好） | 中（新框架） | 高 |
| 社区成熟度 | 中（较新） | 中 | N/A |
| 灵活度 | 中（框架约束） | 高 | 最高 |

**选择 Spring AI Alibaba 的理由**：
- 项目基于 Spring Boot 3.5，Spring AI 是官方推荐的 AI 框架
- Alibaba 版本对 DashScope（通义千问）有原生支持，省去自定义 Provider
- Advisor 机制（责任链）比 Chain 模式更符合 Spring 开发者的思维习惯
- MCP 模块可直接使用，无需额外引入依赖

**代价**：
- Spring AI 版本迭代较快（当前 1.1.2），API 可能变动
- 部分高级功能（如 Agent 编排）需自行实现

### 4.2 Agent 架构：自研 vs Spring AI 内置

| 方案 | 自研三层架构 ✅ | Spring AI 内置 Agent |
|------|----------------|---------------------|
| 控制粒度 | 完全控制每一步 | 框架封装 |
| SSE 事件定制 | 自定义 8 种事件类型 | 需 hack |
| 前端联动 | AgentTraceCard 精准映射 | 难以适配 |
| 开发成本 | 较高（~600行核心代码） | 低 |
| 可维护性 | 代码量可控 | 受框架版本影响 |

**选择自研的理由**：项目需要前端实时展示 Agent 的思考过程、工具调用轨迹，这对事件推送格式有严格要求。Spring AI 内置的 Agent 封装较深，难以自定义 SSE 事件流。自研的 `BaseAgent → ReAcAgent → ToolCallAgent` 三层架构让每一步都可观测、可推送。

### 4.3 对话记忆：文件存储 vs 数据库 vs Redis

| 方案 | 文件存储 (Kryo) ✅ | PostgreSQL | Redis |
|------|-------------------|------------|-------|
| 部署依赖 | 零 | 需数据库服务 | 需 Redis 服务 |
| 读写性能 | 中（单文件） | 高 | 最高 |
| 持久化 | 天然持久 | 天然持久 | 需配置 AOF |
| 并发安全 | 差（无锁） | 好 | 好 |
| 查询能力 | 无 | 强 | 有限 |
| 适合阶段 | 开发/演示 | 生产 | 生产 |

**选择文件存储的理由**：当前是学习演示项目，避免引入数据库依赖。Kryo 序列化性能远超 Java 原生（10-100x），文件存储足够单用户使用。代码中预留了接口（`ChatMemory`），生产环境可无缝切换到 Redis/PostgreSQL 实现。

### 4.4 前端通信：SSE vs WebSocket vs 轮询

| 方案 | SSE ✅ | WebSocket | 长轮询 |
|------|-------|-----------|--------|
| 方向 | 服务端→客户端单向 | 双向 | 客户端→服务端 |
| 实现复杂度 | 低 | 中 | 中 |
| 浏览器支持 | 好 | 好 | 好 |
| 断线重连 | 原生支持 | 需自行实现 | N/A |
| 适用场景 | AI 流式输出 | 实时聊天 | 状态同步 |

**选择 SSE 的理由**：AI 对话是典型的单向推送场景（LLM 生成文本块 → 推送给前端），SSE 是最轻量的方案。且 Spring 的 `SseEmitter` 和 `Flux<String>` 原生支持，前端 `EventSource` API 使用简单。

### 4.5 向量存储：内存 SimpleVectorStore vs PGVector

| 方案 | SimpleVectorStore ✅ | PGVector |
|------|---------------------|----------|
| 部署 | 零依赖 | 需 PostgreSQL + pgvector 插件 |
| 数据规模 | 适合 <10万条 | 百万级以上 |
| 持久化 | 仅内存 | 持久化 |
| 检索性能 | 暴力搜索 O(n) | HNSW 索引 O(log n) |
| 配置 | 一行代码 | 需 DDL + 连接池 |

**选择 SimpleVectorStore 的理由**：恋爱大师的文档集很小（几个 Markdown 文件），内存向量存储足够。代码中注释了 PGVector 配置，切换只需取消注释 pom 依赖和 application.yml 配置。

### 4.6 搜索引擎：SearchAPI.io vs 自建爬虫

| 方案 | SearchAPI.io ✅ | 自建爬虫 |
|------|----------------|----------|
| 搜索质量 | 真实百度结果 | 取决于实现 |
| 法律风险 | 合规 API | 爬虫可能违规 |
| 维护成本 | 零 | 需维护反爬策略 |
| 成本 | 免费额度 + 付费 | 服务器成本 |

## 六、核心设计决策记录（ADR）

### ADR-1：选择 ReAct 模式作为 Agent 核心循环

- **背景**：需要一个让 LLM 能自主使用工具解决问题的 Agent 架构
- **决策**：采用 ReAct（Reasoning + Acting）模式，每步先思考再行动
- **理由**：相比纯 CoT（Chain of Thought）或纯工具调用，ReAct 兼顾推理质量和执行效率。思考过程可展示给用户，增强可解释性
- **代价**：每步消耗更多 Token（思考+行动两次调用 LLM）
- **替代方案**：Plan-and-Execute（先规划再执行）——适合超长任务但首步延迟高

### ADR-2：SSE 结构化事件设计（8 种事件类型）

- **背景**：前端需要实时展示 Agent 的内部执行过程
- **决策**：定义 `AgentStreamEvent` 包含 8 种 type + 结构化字段
- **理由**：相比纯文本流，结构化事件让前端可以精确渲染（思考折叠、工具参数高亮、步骤进度条），用户体验远优于纯文本流
- **代价**：前后端需维护一致的事件协议（通过 `agentStream.js` 统一管理）

### ADR-3：禁用 Spring AI 内置工具调用机制

- **背景**：`ToolCallAgent` 中设置了 `internalToolExecutionEnabled(false)`
- **决策**：手动管理工具调用的消息上下文
- **理由**：Spring AI 内置机制会在工具调用后自动递归调用 LLM，开发者无法在中间插入 SSE 事件推送。禁用后自行调用 `toolCallingManager.executeToolCalls()`，可以在工具执行前后精确推送事件
- **代价**：需自行处理 conversationHistory 的拼装逻辑

### ADR-4：文件存储对话记忆 + Kryo 序列化

- **背景**：需要持久化多轮对话上下文
- **决策**：`FileBasedChatMemory` + Kryo + 滑动窗口
- **理由**：零依赖、高性能、实现简单。Kryo 的序列化速度是 Java 原生的 10-100 倍，滑动窗口控制文件体积
- **代价**：不支持并发写入同一会话、不支持跨会话查询
- **迁移路径**：实现 `ChatMemory` 接口的 Redis/PostgreSQL 版本即可无缝替换

### ADR-5：MCP 协议集成图片搜索

- **背景**：需要为 Agent 扩展图片搜索能力
- **决策**：通过 MCP 协议集成独立服务，而非直接集成 Pexels SDK
- **理由**：MCP 是 AI 工具标准化的趋势协议，一次集成可被多个 Agent 复用。独立服务隔离了第三方 API 依赖和密钥管理
- **代价**：stdio 进程间通信有额外延迟（约 10-50ms），增加了一个需维护的子进程

## 七、总结

本系统是一个**以 ReAct Agent 为核心、以 Spring AI Alibaba 为 AI 基础设施的全栈 AI 应用平台**。架构清晰、分层合理，当前实现满足了学习演示的需求。主要技术取舍点集中在**灵活性 vs 框架约束**和**简单部署 vs 生产可靠**两个维度上。未来演进的核心路径是：存储层升级 → 认证鉴权 → 服务拆分 → Agent 编排 → 平台化。每个演进节点都有明确的触发条件和优先级，可循序渐进推进。
